- Measure rows before full key generation: `$HOME/.compact/versions/0.31.1/x86_64-unknown-linux-musl/zkir mock-compile node_modules/pob-rollup-check/zkir/closeGame.zkir`. `mock-compile` performs circuit synthesis/modeling, not proof generation, and can itself be slow for large circuits. Instruction counts are not row counts.
- Proven cost pitfall: converting a small product to `Bytes<32>` just to read byte 2 causes repeated full-field decompositions in ZKIR v2. `boundedDraw` has `u <= 65535`, literal ranges <=52, and product <=3407820, so `Bytes<3>` preserves the result. The compiled one-draw probe measured 11284 rows wide versus 839 narrow. Exhaustive comparison covered all 65536 inputs for ranges 13 and 46..52 (524288 combinations). Do not narrow the full hash digest: unlike this product, it needs 32 bytes.
- Official explanation: `midnightntwrk/midnight-ledger`, commit `9f9842ebed66cdff0f54d3fb09efc6a7cd077ed8`, `zkir/src/ir_vm.rs:716-726` implements `DivModPowerOfTwo` with `assigned_to_le_bits(..., None, true)`. The ledger-8 branch corroborates the installed-toolchain measurements; do not assume newer main-branch optimizations apply.
- Empty key files and an active compiler process are NOT evidence of completed key generation. Record exit status, complete artifacts and an actual proof/verification separately. Run expensive key builds serially to avoid memory contention.

Passing mirror-based simulator tests does not resolve these blockers.
